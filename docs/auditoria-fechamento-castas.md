# Auditoria de fechamento do Castas Android

**8 de novembro de 2026 · Base Android `2a133da` · Referência web `ca2ca90`**

A auditoria anterior registrou o estado da primeira entrega. Este relatório avalia as correções, a validação em Android 8.0 e Android 16 e a preparação do pacote para assinatura pelo responsável. [Auditoria anterior](auditoria-castas-android.md).

## O que aconteceu com o emulador e como prevenir

O **AVD** é a configuração da máquina virtual, a **imagem do sistema** é o Android convidado, o **ADB** instala apps e comunica com o convidado, e **KVM** acelera a CPU virtual no Linux. SwiftShader pode renderizar a GPU por software enquanto KVM acelera a CPU. Na primeira tentativa, o sandbox ocultava `/dev/kvm`, mas o anfitrião tinha KVM. Iniciei o AVD com `-accel off` mesmo no anfitrião, e o ADB permaneceu offline durante a observação. O script ainda tentou usar `status`, uma variável reservada do Zsh, por isso a espera anunciada não foi uma medição confiável. O diagnóstico anterior atribuiu ao computador uma limitação do sandbox.

No fechamento, executei `emulator -accel-check` no anfitrião e obtive sucesso. As duas imagens são distintas. API 26 usa x86 e API 36 usa x86_64. O AVD Android 8.0 também expôs outra condição. O volume de home tinha pouco espaço para reservar a partição virtual. A execução da auditoria usou dados de AVD sob `/tmp/castas-release-avds`, com mais espaço livre. A checagem agora tem um script versionado. Ele verifica aceleração no contexto real, serial ADB, `sys.boot_completed=1` e API. Um ADB `device` sozinho confirma o transporte, enquanto a propriedade confirma o fim do boot. [Preflight](../android/tools/android-preflight.sh), [aceleração do emulador](https://developer.android.com/studio/run/emulator-acceleration).

No primeiro AVD API 36, o Android registrou um ANR ao iniciar a instrumentação. Uma tentativa posterior chegou à seleção do emoji, mas a captura opcional retornou sem imagem durante um ANR da interface do Android. Troquei a imagem pelo perfil oficial de 16 KiB, reduzi a resolução física mantendo as dimensões em dp, e separei a captura do teste de comportamento. A suíte passou nesse ambiente.

Para abrir o projeto no Studio usando os AVDs desta auditoria enquanto os dados temporários estiverem disponíveis, feche a IDE e inicie-a pelo terminal com `ANDROID_AVD_HOME=/tmp/castas-release-avds /opt/android-studio/bin/studio.sh`. No Device Manager, selecione `CastasApi26` para testar o Android 8.0. Confira o SDK e o Gradle JDK antes de pressionar **Run**. Se o AVD ainda tiver o Castas de release assinado para esta auditoria, remova essa instalação de teste do AVD antes de instalar o APK de debug. Para uso permanente, escolha uma pasta de AVD em um volume com espaço suficiente.

Para projetos novos, execute o preflight e uma jornada mínima em aparelho ou emulador antes de começar a implementação em escala. Registre o SDK, a imagem, a ABI, o espaço e o contexto de execução. Em máquina virtual, a aceleração pode depender de KVM exposto ou virtualização aninhada. Em um sandbox com acesso restrito a sockets ou cache, use uma execução autorizada no anfitrião e um cache Gradle gravável. A alternativa prática é um aparelho de teste ou um runner com virtualização.

## Instalação, Studio, tablets e publicação

1. **Neste Linux.** Abra a pasta `android/` no Android Studio em `/opt/android-studio`. Use o SDK `/home/dever/Android/Sdk`, a plataforma 36, Build-Tools 35.0.0 e JDK 21 para o Gradle. Depois do Gradle Sync, selecione o módulo `app` e o dispositivo no Device Manager. Para emuladores, use uma partição de dados com espaço suficiente e confirme o boot com o preflight. Validei o projeto pelo Gradle Wrapper e ADB. A sincronização pela interface do Studio fica para o teste de uso. [README](../android/README.md).
2. **No celular.** Habilite depuração USB, conecte com um cabo de dados, confirme a chave RSA e confira `adb devices -l`. Rode `adb -s SERIAL install -r android/app/build/outputs/apk/debug/app-debug.apk` na raiz do projeto. Use respostas fictícias. Se já houver uma versão com o mesmo ID e assinatura diferente, o Android recusa a atualização. Desinstalar apaga o resultado local. Em aparelho certificado no Brasil, o ADB é o caminho direto de teste para um APK ainda não registrado. [Dispositivo físico](https://developer.android.com/studio/run/device), [verificação de desenvolvedores](https://developer.android.com/blog/posts/android-developer-verification-rolling-out-to-all-developers-on-play-console-and-android-developer-console).
3. **Compatibilidade.** Android 8.0 corresponde à API 26. O mínimo determina se o APK pode ser instalado e o target determina as regras e os comportamentos de plataforma que o app adota. Para preservar o suporte, mantenha o mínimo, inspecione dependências e manifesto mesclado, rode lint e repita a jornada no Android 8.0 sempre que mudar recursos, APIs ou bibliotecas. API 36 é o target aplicável aos novos apps de celular na Play. [Regra Play](https://support.google.com/googleplay/android-developer/answer/11926878).
4. **Tablets.** Use o mesmo APK. A largura de conteúdo é limitada a 640 dp, há rolagem e a sessão resiste à recriação da Activity. Valide janelas estreitas, tablet e fonte grande. Uma disposição de duas colunas pode ser útil se testes mostrarem que melhora a leitura. Use a largura da janela e as necessidades da tarefa para decidir o layout. Um app separado só se justifica se as funcionalidades ou a distribuição forem distintas. [Layouts adaptativos](https://developer.android.com/develop/adaptive-apps/guides/support-different-display-sizes).
5. **Outras IDEs.** Gradle Wrapper e ADB também podem ser usados no terminal do IntelliJ IDEA, VS Code ou outro editor. A sincronização Android, Compose Preview, Device Manager e profiler têm suporte próprio do Studio. Para novos projetos, coloque a matriz de JDK, SDK, AGP e Gradle em `android-module-structure`, garanta importação da raiz, documente comandos CLI e peça evidência de Gradle Sync quando a IDE fizer parte do aceite.
6. **Play Console.** O próximo passo do responsável é confirmar direitos das imagens, identidade do pacote e versão, obter a chave de upload, assinar o AAB e configurar Play App Signing. Enviar primeiro para teste interno, com política de privacidade pública coerente, Data safety, screenshots e classificação. Contas pessoais criadas após 13/11/2023 seguem a regra aplicável de teste fechado com 12 participantes por 14 dias contínuos antes de solicitar produção. Um telefone real deve confirmar instalação e atualização pelo canal. [Checklist de release](production.md), [regras de teste fechado](https://support.google.com/googleplay/android-developer/answer/14151465).

Depois do teste interno, vale observar se as pessoas entendem a distinção entre “ver último resultado”, “iniciar novo teste” e “copiar”. A próxima melhoria pode ser a opção de apagar o resultado no app ou o Android Sharesheet. Cada uma muda comportamento e deve ter change própria, com atenção à privacidade.

## OpenSpec, PDF e documentação de referência

O OpenSpec é o dono do contrato e das tarefas. Na primeira entrega a CLI criou a raiz, mas a geração da integração Codex falhou com `EROFS`. O fechamento retomou a change original para comportamento e criou uma segunda para toolchain e release. A CLI local faz status, validação e consolidação. O aceite depende dos checks executáveis, e publicar tem autorização e credenciais próprias. O guia SDD revisado (PDF externo ao repositório) descreve esse processo. [OpenSpec](https://github.com/Fission-AI/OpenSpec).

O PDF já recomenda separar documentação, mudanças e evidências, confirmar a toolchain, implementar por fatias, revisar e só arquivar após os gates. O fluxo atual incorpora essas etapas. A alteração que faria no PDF é acrescentar um caso concreto de portabilidade com **fonte → divergência → decisão → teste → resultado**, preflight no anfitrião e gates distintos para consolidar a spec, gerar o pacote e publicá-lo. A versão da CLI efetivamente instalada e a descoberta das skills devem ser verificadas, pois o perfil gerado muda conforme o host.

A pasta `docs/artifacts` da web foi usada. Ela forneceu as perguntas, wireframes, mockup, limites da pontuação, visualização, texto a copiar e imagens. A implementação React esclareceu a numeração por dimensão, o bloqueio de toque durante a transição e o tempo da confirmação de cópia. Para uma portabilidade sem adivinhação, faltavam decisões sobre rotação e morte de processo, armazenamento indisponível, versão de Android, fonte de emojis, TalkBack, janelas grandes, direitos das imagens, política Android e assinatura. O conflito do wireframe demonstrou a necessidade de vetores canônicos versionados. [Artefatos web](artifacts/).

## Modelos, fatias e fábrica de software

O histórico não permite medir um efeito causal do GPT-6 Luna. Os erros de lifecycle e contraste eram reproduzíveis e a confusão sobre KVM envolvia a execução. A maneira de comparar modelos é fixar revisão, ferramentas, critérios e tempo, então medir regressões detectadas, falsos positivos, evidência de runtime, retrabalho e custo. Para um modelo principal de custo equilibrado usaria GPT-6.1 Sol. Para decisões ambíguas ou revisão de maior impacto usaria GPT-6 Astra. Luna é apropriado para fatias pequenas com oráculo claro, como converter catálogos e portar vetores. [Modelos no Codex](https://learn.chatgpt.com/docs/models), [escolha de modelos para subagentes](https://learn.chatgpt.com/docs/agent-configuration/subagents#choosing-models-and-reasoning).

Um prompt amplo pode autorizar o app inteiro. A execução deve seguir fatias verticais com checkpoints. Neste caso, primeiro rodar uma tela no aparelho, depois questionário com gravação, então paridade e acessibilidade, por fim release. Para Luna, fixe contratos curtos, comandos e resultados esperados, condição para parar e registrar bloqueio, e próxima ação. Em vez de carregar várias skills ao mesmo tempo, selecione uma dona do artefato e um helper que execute a fronteira.

Uma coleção própria pode substituir o uso direto das skills de Matt em cinco passos:

1. **Bootstrap SDD.** Criar uma skill pequena de entrega, com preflight, inventário de skills e adaptador à CLI OpenSpec. Usar PentaPRO para produto e decisões e OpenSpec para specs, changes, cenários e tarefas.
2. **Implementação por fatias.** Criar uma skill geral de TDD e implementação com teste vermelho pelo motivo correto, verde mínimo e refatoração. Incorporar modelagem de domínio e desenho de interfaces como referências de PentaPRO e manter UI Design como dona de telas e estados.
3. **Diagnóstico.** Adotar um procedimento reproduzível que separe falhas de host, sandbox, toolchain, dependência, plataforma e código. A evidência precisa mostrar revisão, dispositivo/ambiente, comando, resultado e lacunas.
4. **Revisão e release.** Estender Peer Review com dois eixos independentes, conformidade com o contrato e padrões do projeto. Cybersecurity continua dono dos riscos. Um helper de release por plataforma cobre artefato, assinatura, ambiente, atualização, suporte e recuperação. Preserve avisos MIT e atribuições ao adaptar material.
5. **Avaliação.** Exercite a coleção em projetos descartáveis Android, web, iOS e desktop. Inclua pelo menos uma falha esperada por plataforma, documentação contraditória, retomada e uma revisão com achado semeado. Só adicione novos entrypoints quando os gatilhos e saídas se distinguirem dos existentes.

As ferramentas com valor imediato para o Castas já são Studio, ADB, emulador/KVM, Gradle Wrapper, lint, OpenSpec e Bundletool. Acrescente um runner com virtualização ou um aparelho para automatizar o gate de runtime. Um GitHub Actions verde deve comprovar os checks que ele executa. Registre a evidência de dispositivo separadamente se esse job não tiver emulador. Para projetos web, Playwright e axe complementam a inspeção manual. Para iOS, Xcode em macOS é a toolchain de execução e assinatura.
